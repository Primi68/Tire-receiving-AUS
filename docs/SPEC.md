# Tire Receiving 제품 명세

문서 기준 버전: **0.1.0 MVP**

## 1. 목적

현장에서 언로딩된 타이어를 확인할 때 노트 앱과 계산기를 번갈아 쓰는 시간을 줄인다. 작업자는 타이어와 랙 색상을 고르고 2×2 랙 묶음 수와 나머지만 입력한다. 앱은 실제 수량, 정상 트레일러 예상 수량과의 차이, 부분 입고 잔량을 계산해 하나의 검수 기록으로 저장한다.

## 2. 운영 흐름

Unloading schedule 확인은 현장에 내려가기 전에 예상 타이어를 파악하는 사전 작업이다. 0.1.0은 schedule 자체를 연동하거나 저장하지 않는다.

1. 모니터의 Unloading schedule에서 예정 Trailer, Dock, 타이어를 확인한다.
2. Floor에서 실제 타이어 이름, 랙 색상, 랙당 적재량과 적재 상태를 확인한다.
3. 앱에서 타이어를 이름 또는 별칭으로 검색한다.
4. Blue/Orange 랙 색상을 선택한다.
5. 자동으로 제시된 계산식이 실제 적재와 맞는지 확인한다.
6. 다르면 랙당 적재량, 묶음 수, 추가 수량 또는 직접 실측 총수량을 수정한다.
7. 완료·검수 중·Pending·부분 입고 상태와 날짜, Dock, Trailer, 메모를 저장한다.
8. 기록 목록에서 검색·필터·수정·삭제하거나 한 줄 요약을 복사한다.
9. 근무 종료 전 JSON 백업을 내보낸다.

## 3. 수량 계산

### 3.1 기본식

```text
실제 수량 = 랙당 적재량 × 4 × 묶음 수 + 추가 수량
차이 = 실제 수량 - 예상 수량
```

`4`는 2×2로 정리된 랙 한 묶음의 랙 개수다.

### 3.2 자동 제안

타이어와 랙 색상을 선택하면 앱은 해당 색상의 `qtyPerRack`과 타이어의 `expectedQty`로 기본 묶음 수와 추가 수량을 계산한다.

```text
묶음 단위 = 랙당 적재량 × 4
묶음 수 = floor(예상 수량 ÷ 묶음 단위)
추가 수량 = 예상 수량 mod 묶음 단위
```

예상 수량 756, Orange 랙당 20개라면 묶음 수 9, 추가 수량 36을 제안해 `20 × 4 × 9 + 36 = 756`을 표시한다.

### 3.3 현장 수정

- 작업자는 랙당 적재량, 묶음 수, 추가 수량을 각각 수정할 수 있다.
- 랙 적재 형태로 설명하기 어려운 경우 실측 총수량을 직접 입력할 수 있다.
- 수정된 랙당 적재량을 선택한 색상의 새 프리셋으로 저장할 수 있다.
- **예상 수량으로 확정**은 현재 랙당 적재량을 기준으로 식을 다시 유도해 차이 0인 기록을 만든다.
- **현재 값으로 저장**은 실측 계산 또는 직접 입력 값을 그대로 기록하고 차이를 보존한다.

## 4. 랙 색상과 프리셋

랙 색상은 `blue`와 `orange` 두 종류다. 규격이 다르므로 프리셋은 **타이어 + 색상** 조합으로 관리한다. 한 타이어에 한 색상만 또는 두 색상 모두 등록할 수 있다.

프리셋이 저장하는 값:

- 랙 색상
- 랙당 적재량(`qtyPerRack`)
- 기본으로 먼저 선택할 색상(`defaultColor`)

묶음 수와 추가 수량은 별도 고정값으로 저장하지 않고 현재 예상 수량과 랙당 적재량에서 다시 계산한다. 따라서 예상 수량이나 적재량을 바꾸면 계산식 미리보기도 함께 갱신된다.

## 6. 타이어 마스터 기능

사용자는 다음 값을 추가·수정할 수 있다.

- 표시 이름
- 쉼표로 구분한 검색 별칭
- 트레일러 정상 예상 수량
- Blue 프리셋 사용 여부와 랙당 적재량
- Orange 프리셋 사용 여부와 랙당 적재량
- 기본 랙 색상

Blue 또는 Orange 프리셋이 최소 하나 필요하다. 기존 타이어 마스터 삭제는 확인 대화상자를 거친다. 해당 타이어의 과거 검수 기록은 당시 이름과 수량 스냅샷을 유지하지만, 삭제된 마스터의 기록을 다시 편집하려면 타이어를 먼저 다시 등록해야 한다.

## 7. 검수 기록

기록 한 건은 다음 정보를 가진다.

| 분류 | 필드 |
| --- | --- |
| 식별 | 기록 ID, 생성 시각, 수정 시각 |
| 일정 | 검수 날짜 |
| 타이어 | 타이어 ID, 저장 당시 타이어 이름 |
| 적재 | 랙 색상, 랙당 적재량, 묶음 수, 추가 수량, 직접 입력 수량 |
| 결과 | 예상 수량, 실제 수량, 차이, 사람이 읽는 계산식 |
| 상태 | 완료, 검수 중, Pending, 부분 입고 |
| 입고 | Dock, Trailer, 부분 입고 수량, 남은 수량 |
| 메모 | 특이사항 |

Trailer 입력은 저장할 때 대문자로 정규화한다. 부분 입고의 남은 수량은 `max(0, 실제 수량 - 받은 수량)`으로 계산한다.

## 9. 저장 모델

| 실행 환경 | 저장 위치 | 백업 방식 |
| --- | --- | --- |
| Android APK | WebView DOM storage / 앱 전용 데이터 | Android 문서 선택기로 JSON 저장·열기 |
| 웹 앱 | 현재 사이트의 브라우저 Local Storage | 브라우저 다운로드·파일 선택 |

저장 키는 `tire-receiving.tires.v1`과 `tire-receiving.records.v1`이다. APK와 웹 앱은 자동 동기화하지 않는다. 복원 시 입력 파일을 검증한 뒤 두 저장 키를 함께 교체하며, 저장 실패 시 이전 로컬 값을 되돌린다.

## 10. Android 범위

- Package: `com.primi.tirereceiving`
- Version: `0.1.0`, `versionCode 1`
- 최소 OS: Android 8.0 / API 26
- `dist/` 정적 파일을 APK assets로 직접 포함
- 앱 내부 가상 HTTPS 호스트에서만 정적 파일 로드
- 외부 URL 이동 차단
- Android Manifest에 `INTERNET` 권한 없음
- WebView 파일 및 content 직접 접근 비활성화
- 앱 백업(`android:allowBackup`) 비활성화
- 사용자 동작에 한해 클립보드 복사와 JSON 문서 생성·선택 사용

## 11. 0.1.0에 포함하지 않는 기능

- Unloading schedule 시스템 연동
- 로그인, 사용자 권한, 서버 데이터베이스
- 여러 기기 또는 APK와 웹 간 자동 동기화
- 카메라, OCR, 바코드 스캔
- 위치 정보, 푸시 알림
- 자동 Trailer/Dock 배정
- 생산 라인 Validation, Feeding, TPMS·너트·밸브·캡 재고 관리

## 12. 완료 기준

- 초기 타이어가 정확히 14개이며 각 예상 수량과 프리셋이 명세와 일치한다.
- 모든 대표 계산식이 예상 수량을 재현한다.
- 등록된 색상 선택 시 랙당 적재량과 계산식이 자동 제안된다.
- 계산값이 다르면 차이가 표시되고 수정값을 저장할 수 있다.
- 네 가지 상태와 날짜·Dock·Trailer·부분 수량·메모를 보존한다.
- 기록과 타이어 마스터를 검색·수정할 수 있다.
- 유효한 JSON은 복원되고 잘못된 JSON은 현재 데이터를 교체하지 않는다.
- APK는 네트워크 없이 정적 화면, 계산, 저장, 백업·복원을 사용할 수 있다.
- release APK는 프로젝트의 고정 서명 인증서와 일치할 때만 배포한다.
